# C++ SDK 使用指南

[English](guide.md) · [README](../README.md)

## 1. 安装与边界

SDK 与三个 CLI Demo 以 [MIT](../LICENSE) 许可在 [tansrai/tansr-cpp](https://github.com/tansrai/tansr-cpp) 提供源码。从 **[v0.1.0 正式发行](https://github.com/tansrai/tansr-cpp/releases/tag/v0.1.0)** 下载源码包、匹配平台的 SDK 或独立 Demo 包，并按同版校验清单核对摘要。二进制覆盖 Windows x64、Linux x64 和 macOS arm64；Conan/vcpkg 使用同版自有配方包，尚未进入社区公共索引。

库使用 C++17、CMake 3.25+，以下命令使用 Ninja。二进制 SDK 包解压后包含 `include/`、`lib/`、`dependencies/` 和 `share/TansrSDK/`；保留这个目录结构，只把 SDK 根目录传给 `CMAKE_PREFIX_PATH`，包配置会局部查找捆绑的依赖。二进制 SDK 消费不需要 Node、Go、Rust 或 SDK 源码。

在一个新的应用目录保存以下两个完整文件。这个最小程序核对公开 API、链接与 Runtime 启停，不发送网络请求；真实会话和认证接入见后文。

`CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.25)
project(my_app LANGUAGES CXX)
find_package(TansrSDK 0.1.0 EXACT CONFIG REQUIRED)
add_executable(my_app main.cpp)
target_compile_features(my_app PRIVATE cxx_std_17)
target_link_libraries(my_app PRIVATE tansr::sdk)
enable_testing()
add_test(NAME sdk_startup COMMAND my_app)
```

`main.cpp`：

```cpp
#include <chrono>
#include <iostream>
#include <tansr/crypto.hpp>
#include <tansr/json.hpp>
#include <tansr/runtime.hpp>

int main() {
    auto value = tansr::Json::parse("{\"decimal\":1.25}");
    if (!value || value.value().at("decimal").number_token() != "1.25")
        return 1;
    auto digest = tansr::crypto::sha256_hex("abc");
    if (!digest ||
        digest.value() != "ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad")
        return 2;
    auto runtime = tansr::Runtime::create();
    if (!runtime)
        return 3;
    runtime.value()->stop();
    auto stopped = runtime.value()->shutdown(std::chrono::seconds(30));
    if (!stopped || stopped.value() != tansr::ShutdownStatus::stopped)
        return 4;
    std::cout << "Tansr SDK ready; no network request was made\n";
    return 0;
}
```

v0.1.0 二进制包提供 Release 静态 SDK；使用匹配的编译器/架构/CRT，在应用目录运行：

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH=/absolute/tansr-cpp-sdk-0.1.0
cmake --build build
ctest --test-dir build --output-on-failure
```

Windows 在 x64 Native Tools shell 中运行同样的命令，将前缀换成 `C:/absolute/tansr-cpp-sdk-0.1.0`；Release 保持 `/MD`。不要用这个 Release 制品配置 Debug `/MDd` 应用。

公共头位于 `include/tansr`，不暴露 curl/OpenSSL/JSON 私有句柄。Windows 默认 `/MD` 或 Debug `/MDd`；static/shared、Debug/Release、CRT 不得混配。PImpl 不意味着跨编译器、STL、版本 ABI 稳定。C++20 宿主可使用同一 C++17 API；首版不提供 C ABI、GUI 框架或任意 Shell。

v0.1.0 制品的平台基线如下；以对应制品清单的编译、依赖及最低系统标签为准。源码可重新编译不代表现成二进制兼容更老系统。

| 平台 | 构建与安装要求 |
|---|---|
| Windows x64 | VS 2022 / MSVC 19.44，发行静态 SDK 为 Release `/MD`；`/MDd` 仅用于自行构建的 Debug 版本。构建应用使用 x64 Native Tools shell，运行 Demo 需匹配的 MSVC 运行库 |
| Linux x64 | GCC 13；已在 Ubuntu 24.04 / glibc 2.39 验证。发行二进制实测符号下限为 glibc 2.38、GLIBCXX 3.4.32；这不等于已在所有满足符号版本的发行版验证 |
| macOS arm64 | Apple Clang 21；v0.1.0 制品的最低部署目标为 macOS 26.0，不宣称可在更低版本运行 |

从源码构建时仍须事先准备同配置的 curl 8.22.0、c-ares 1.34.8、OpenSSL 3.5.9，精确来源见 [dependencies.json](../packaging/dependencies.json)。源码默认 CMake 不下载依赖，生成操作目录已入库；源码安装与包配方见[配方](../packaging/README.md)。普通源码安装没有捆绑依赖时，将 SDK 与依赖前缀一并传给应用：

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH="/absolute/tansr-cpp-0.1.0;/absolute/dependencies"
cmake --build build
```

宿主若已有匹配依赖，可显式加 `-DTansrSDK_NO_BUNDLED_DEPENDENCIES=ON`，同时提供自己的依赖前缀。该开关只禁用包配置自动选择 `dependencies/`，不会关闭依赖检查或保证任意版本 ABI 兼容。包配置中的依赖搜索不永久改变应用的前缀设置。

自行构建 Windows 共享库时，应用须能加载 SDK 和依赖的 DLL；部署相应 `bin` 目录及运行库，不能靠开发机全局 PATH 掩盖缺依赖。发行静态 SDK 已带开发依赖，仍须满足制品声明的 OS/CRT 运行条件。

三个 Demo 各有独立制品包，不是 SDK 链接目录。分别解包后，从各自的 `bin/` 调用对应程序；Windows 加 `.exe`。例如将 chat 包解压到 `/absolute/tansr-chat-0.1.0`，运行 `/absolute/tansr-chat-0.1.0/bin/tansr-chat --help`。它们与 Rust Demo 同名，不能覆盖已有安装，凭据与服务地址按下一节设置。

## 2. 认证、当前身份与私有文件

第一次接入前，向 Serve 部署负责人或应用后端取得服务 origin、可用会话 family、短期 token 和当前 scope，并确认所用模型及应用策略已配置。SDK 和 Demo 只连接已有 Serve，不随包启动或配置服务。`--help` 与第 1 节启动程序都不验证这些服务端条件；不带 attach/resume 的 `tansr-chat --message ...` 会创建真实会话并发送业务轮。

Serve 负责验证短期 token、应用配置和当前授权。SDK 不自动登录、不存长期 appkey。Demo 使用 `TANSR_TOKEN_FILE`（单行短期 token）和 `TANSR_SCOPE_FILE`（下列 UTF-8 JSON），二者必须在同一私有目录、不同文件：

```json
{"applicationScopeId":"app-demo","endUserId":"user-demo","authorizationRevision":"1"}
```

这些值必须来自开发者可信后端，且与 token 相符；Demo 文件本身不能授予 Serve 权限。每个请求重读 token，读前后核 scope；每次工具授权及档案访问也核 scope。刷新同主体 token 可以继续；改变应用、用户或授权修订会终止旧客户端操作，须创建新对象并按原资源对账。不会自动换用户重放写入。

文件和其直接目录须仅由当前用户访问；父路径不得含链接、Junction/reparse point，文件不得多硬链接。Unix 使用目录 0700、文件 0600，Windows 使用当前用户所有权及私有 DACL。SDK 拒绝不安全的已有路径，不替用户放宽或重写其 ACL。凭据通过共享只读句柄读取，chat/tools 可同时消费同一目录。

```sh
export TANSR_TOKEN_FILE=/absolute/private-credentials/token.txt
export TANSR_SCOPE_FILE=/absolute/private-credentials/scope.json
export TANSR_BASE_URL=https://serve.example.invalid
```

Windows PowerShell 对应设置（这里只保存文件路径和服务地址）：

```powershell
$env:TANSR_TOKEN_FILE = 'C:/absolute/private-credentials/token.txt'
$env:TANSR_SCOPE_FILE = 'C:/absolute/private-credentials/scope.json'
$env:TANSR_BASE_URL = 'https://serve.example.invalid'
& 'C:/absolute/tansr-chat-0.1.0/bin/tansr-chat.exe' --help
& 'C:/absolute/tansr-tools-0.1.0/bin/tansr-tools.exe' --help
& 'C:/absolute/tansr-archive-0.1.0/bin/tansr-archive.exe' --help
```

Unix 用各自安装前缀下的 `bin/tansr-chat`、`bin/tansr-tools`、`bin/tansr-archive`；后文命令名均指该安装位置。凭据文件须事先由可信宿主写入，环境变量不是 token 内容。

三个 Demo 共用下列参数；使用 `--参数 值`，不要使用 `--参数=值`，含空格的路径须加引号。同一参数不能重复：

| 参数 | 默认值与用途 |
|---|---|
| `--base ORIGIN` | 优先于 `TANSR_BASE_URL`；均未指定时为 `http://127.0.0.1:8787`。填写 origin，不附加 `/api` |
| `--family FAMILY` | 默认 `sdk1`，另一个合法值为 `sdk2-offload-v1`；后续进程须显式保持原 family |
| `--token-file FILE`、`--scope-file FILE` | 分别优先于对应环境变量；值是绝对文件路径，不是 token 或 JSON 本文 |
| `--timeout SECONDS` | 默认 `600`，范围 `1..86400`；约束本次 Demo 工作的总取消时限，包括交互、轮询和等待材料 |

因此默认 tools 循环并非无限运行；需要更长观察时可设置 `--timeout 3600`。这个参数不是“每次请求都重新计时”，也不会延长已经保存的创建/材料意图截止时间。普通 chat/tools 写请求另有 30 秒截止，增加 `--timeout` 不会同时调长这些截止。超时或 Ctrl+C 取消本地工作，不能据此判定 Serve 的写入或业务轮未发生。

ApiClient 接受不含凭据、路径、query 或 fragment 的 HTTP(S) origin；当前实现不按回环/非回环限制 HTTP。建议仅在回环开发使用明文，实际部署使用有效 HTTPS。系统信任与企业 CA 由 `RuntimeOptions.ca_file` 配置，不关闭主机名或链验证。Demo 不把 token 放入命令行、日志、错误 detail 或档案。网络错误仅显示安全错误码；显式诊断 `Error.detail` 可能含业务/服务端内容，宿主须单独保护。

`RuntimeOptions.ca_file` 是 SDK 宿主的配置项；发行 Demo 没有 `--ca-file` 参数，使用默认 Runtime 信任配置。需要显式企业 CA 的应用应通过 SDK 配置该字段，不能给 Demo 添加不存在的参数或关闭证书验证来联调。

## 3. Runtime 与回调生命周期

宿主持有 Runtime 最终所有权；ApiClient、Session 和执行器共享该底座。停止顺序是取消应用工作、退出并 join 应用 worker、调用客户端 shutdown、Runtime stop/shutdown，直到 `ShutdownStatus::stopped` 后才销毁。`pending` 是尚未静止，不是成功。不要在 SDK callback 中等待自己、释放最后一个 Runtime 或卸载 DLL；callback 可以发出取消/stop 请求。

```cpp
#include <tansr/api.hpp>
#include <tansr/session.hpp>

void connect(std::string base, tansr::TokenProvider provider) {
    auto runtime = tansr::Runtime::create();
    if (!runtime) return;
    tansr::ClientOptions options;
    options.base_url = std::move(base);
    options.token_provider = std::move(provider);
    auto api = tansr::ApiClient::create(std::move(options), runtime.value());
    if (api) {
        auto sessions = tansr::session::SessionClient::create(api.value());
        // 使用显式 Result 检查，业务代码在此消费 sessions。
        api.value()->shutdown();
    }
    runtime.value()->stop();
    auto stopped = runtime.value()->shutdown(std::chrono::seconds(30));
    // 宿主应在此处理错误/pending，并保留仍被工作引用的 Runtime。
    (void)stopped;
}
```

`CancellationToken` 只取消本地请求/观察，不自动调用 Serve interrupt、close 或 ACK。网络字节、Json、事件和 Result 拥有存储；不要将临时引用捕获到生命周期之外。业务 handler 应合作观察 cancellation；SDK 不安全强杀 C++ 线程。

## 4. 会话 Demo

```sh
tansr-chat --base http://127.0.0.1:8787 --message "你好"
tansr-chat --family sdk2-offload-v1 --prepare-create /absolute/intents/session.json --request-id app-create-001
tansr-chat --family sdk2-offload-v1 --create-intent /absolute/intents/session.json
tansr-chat --attach SESSION_ID
tansr-chat --resume SESSION_ID --last-event-id 42
```

默认 `sdk1`；新族必须明确 `--family sdk2-offload-v1`。新族创建的 `--request-id` 由调用者保存；失回后保留原意图，不生成新 ID 重建。`--attach` 连接已有 live 会话，`--resume` 使用原恢复入口，两者不能互换或同时提供。给活动轮发送 `--message` 会拒绝，不能悄悄新开轮。

推荐按上面两步创建 offload 会话：`--prepare-create` 在同一个私有文件内原子保存原 `requestId`、可选 `--model`、完整创建 body、传输请求键、绝对截止时间及 base/family/当前授权归属，不发送请求；`--timeout` 决定准备时的意图有效期。`--create-intent` 读取原值调用公开 `SessionClient::create`，成功只输出 `session:`，不会启动或重发业务轮。随后使用同族 `--attach SESSION_ID` 对话。发生创建失回时在原截止时间内重跑同一 `--create-intent` 命令，不重新准备、不换键、不延长截止。SDK2 的会话创建会由 Serve 自动建立 Source/binding；恢复原会话创建也恢复该归属，不伪造手动 binding epoch。

两个意图命令不接受 `--message`、`--last-event-id`、`--resume`、`--attach`，恢复还禁止覆盖 `--model` 或 `--request-id`。已有文件、非法格式、过期、跨 origin/family/应用/用户/授权修订均失败；原文件保留供对账。原直接 `--request-id` 创建方式仍可用，但要求应用自行可靠保存完整意图，不能仅凭同一 ID 声称请求 body 和截止时间已保全。

流在发送前打开，`TurnTracker` 从发送前 seq 与实际 turnId 识别本轮终态。202、EOF、旧轮完成或 session.ended 都不代表本轮完成。每个新轮创建新 tracker。`--last-event-id` 是处理游标，不能拿档案 ACK、水位或历史代际替代；发生 gap 必须对账，Demo 不自动跨缺口前移。

交互命令：

| 命令 | 行为 |
|---|---|
| `/interrupt` | 显式请求远端中断，继续等待实际终态 |
| `/allow TICKET`、`/deny TICKET` | 仅回答当前实收、未关闭票据及原 digest，默认不批准 |
| `/answers TICKET JSON_ARRAY` | 回答实收问题；每项含 questionId、selectedOptionIds 和可选 freeText |
| `/target` | 查询当前同轮输入目标及能力 |
| `/insert JSON_OBJECT` | 明确 inputId、target.historyEpoch/turnId、content.text、可选 ack；不替换当前轮 |
| `/history` | 读取 history(0,0) 计数视图，0 是合法 limit |
| `/quit` 或 Ctrl+C | 停止本地观察，不宣称 Serve 已停止 |

```text
/insert {"inputId":"input-001","target":{"historyEpoch":"原值","turnId":"原值"},"content":{"text":"补充要求"},"ack":"memory"}
```

请求 durable 但服务不支持时原样失败，不降级为 memory。accepted/received 不等于 consumed。`--message` 非交互遇审批/问答会非零退出，并保留 session 供交互接续；不自动同意。

先执行 `/target` 取得当前原始目标，再填写 `/insert`，不要把示意中的“原值”当作实际 ID。控制命令回执会立即刷新到标准输出，即使模型正在等待也可由管道宿主读取。`/interrupt` 收到受理后仍等待真正的 `turn.aborted`；本 Demo 对中断轮非零退出，不显示 `[turn completed]`。`/quit` 只结束本地观察，原活动轮仍可重新 attach。

SDK 还提供 `send_blocks`（TextBlock/ImageBlock）、`transcribe`、`speak`、checkpoints/checkpoint/restore/export/import/delete、compact、cwd 和 application_prompt_meta。调用 STT/TTS 不等于录音/播放器或主模型原生音视频块。平台、Serve 与请求配置的系统提示词合成由核心控制，C++ 不额外拼接覆盖；应用应读原 meta/配置能力了解当前实际策略。

## 5. 显式终端业务工具

```sh
tansr-tools --journal /absolute/private-journal --require-output
# 另一个终端使用上条输出的会话 ID
tansr-chat --attach SESSION_ID
```

先等待 tools 输出 `session:` 和 `ready:`，再启动第二个终端。两个终端分别设置相同的凭据路径和 base，并使用 tools 输出的 family；新终端不自动继承另一终端临时设置的环境变量。不带 `--session` 的 tools 会创建会话；连接已知会话用 `--session SESSION_ID`，而不是 chat 的 `--attach` 参数。重启执行器时保留原 journal 和执行器标识（`--executor` 默认 `cpp-demo`），例如：

```sh
tansr-tools --family sdk1 --session SESSION_ID --executor cpp-demo --journal /absolute/private-journal --require-output --timeout 3600
```

既有会话仍须允许当前 `DemoOrderStatus` 能力绑定，复接不会绕过 Serve 策略。新建 offload 会话时，tools 还要求调用者保全的 `--request-id STABLE_ID`；已经拿到会话 ID 后用同族 `--session` 复接。journal 只记录执行事实，不代替耐久的会话创建意图。journal 中的未确认事实继续保留，不能因重启而重新执行结果不明的业务。

Serve 应用策略须允许 `DemoOrderStatus`；示例注册一个只读合成订单函数，不装 Shell、文件工具或任意执行器。注册→initialize→首次 bind→可选 output 协商→Runner 完整消费公开 SDK。询问“查询订单 DEMO-001”后输出第一块 stdout、750ms 合成等待、stderr，再由 Runner 封 seal。`capture` 只说明采集，output ACK/seal 与业务回执分开；任何输出失败都不能重跑业务 handler。

`--run-once` 处理一个排队 operation 并退出，适合联调；默认持续领取且续租，Ctrl+C 合作取消。FileJournal 是私有明文事实账本，保存原操作认领和确定回执，不是加密档案。只有能证明零副作用才能返回 `ToolFailure::rejected`，异常、不能确定的取消或输出失回是 unknown。业务 `{status:"error"}` 可以是已确定的业务结果。

Demo 授权器每次读当前 scope，核 app/user/revision/session/binding/workspace/tool。生产应用仍须接入实时撤权与资源政策；不能把注册平台当成权限或设备失败后回落 Serve 宿主。

## 6. 本地档案与材料

Source/provider 由 Serve 宿主事先登记；Demo 不发明注册 URL。使用独立目录存档案和意图。设置 `TANSR_ARCHIVE_KEY_FILE` 为私有的 64 位十六进制 AES-256 密钥文件；一 key 只供一个档案，`--key-id` 由宿主管理。密钥不放档案旁边、不在解密失败时自动更换；密钥轮换使用 FileStore 显式 API。

先确定使用哪一个 binding：尚无 binding、且宿主支持手工绑定的 SDK1 会话，才使用下面的 prepare-create/create 步骤。offload 会话创建时已经由 Serve 建立 Source/binding，应复用其原 binding，直接进入 sync/status；不要再创建一份。binding ID 由可信宿主提供，SDK 应用也可通过 `ArchiveClient::binding_target(SESSION_ID)` 读取；Demo 没有 `--mode target`。每次运行 offload 档案命令都须加 `--family sdk2-offload-v1`，不能沿用下列默认 SDK1 示例而漏掉 family。

```sh
tansr-archive --mode prepare-create --session SESSION --source SOURCE --request-id bind-001 --intent /absolute/intents/create.json
tansr-archive --mode create --intent /absolute/intents/create.json
tansr-archive --mode creation-status --intent /absolute/intents/create.json
tansr-archive --mode sync --binding BINDING --file /absolute/archive/history.bin --key-id local-key-1
tansr-archive --mode status --binding BINDING
tansr-archive --mode recover --binding BINDING --file /absolute/archive/history.bin --key-id local-key-1 --request-id recover-001
tansr-archive --mode materials --binding BINDING --file /absolute/archive/history.bin --key-id local-key-1 --request-id response-001 --intent /absolute/materials/response.json
tansr-archive --mode material-submit --intent /absolute/materials/response.json
tansr-archive --mode material-status --intent /absolute/materials/response.json
```

每条命令都携原 `--family`、同 Base URL 和 scope；意图旁的 `.owner` 文件拒绝改族/身份重放。prepare-create 先持久保存原 body/requestId/epoch/绝对截止才允许 create；prepare 不创建 binding。截止到期不能改时间或换键；使用 status 对原操作查账。已有意图绝不覆盖，文件只写入一半时保留现场，不把失败打印成功。

FileStore 核页链、记录/正文/附件摘要及当前身份，整页+附件+pending ACK 原子耐久后才发送 ACK。sync 的 complete、recover 的已确认原 pending、水位 coverage 和材料消费是不同事实。recover 只处理原 pending/明确 stale 的显式恢复，不替代完整同步；一般 412、撤权和已过期 epoch 不自动 rebase。

sync 默认每次最多处理 64 页；`--max-pages` 可设为 `1..1024`。达到页数上限会非零退出，继续时使用原 binding/file/key，不删除档案；recover 确认原 pending ACK 后，仍需 sync 剩余页。recover/materials 要求原档案文件已经存在。materials 等待一个真实的当前材料请求，无请求时会等到本次取消时限；material-status 输出 received 后非零退出，表示尚未确认 core-consumed，不等于可以换意图重传。

materials 只订阅当前 request，把首次收到的 remaining TTL 固定为绝对截止，并保存 `.request` 原意图；只回供点名且已验证记录。准备/分块/等待都不续期，最终 response 落盘后 submit。失回用原 response 的 `material-submit` 或 `material-status` 对账；received 不宣称 core-consumed。材料、档案、执行日志不成为第二套上下文、审批或计费权威，也不代表记忆全本地化、多副本备份或跨 SDK 私有介质兼容。

## 7. 状态、故障与交付

`Result<T>` 必须检查；未确认结果保留原 ID/请求/截止/介质。`ApiClient::retry_same_request` 仅在原错误允许且同请求见证一致时使用，不作为通用自动重试。默认错误日志不输出 raw detail、token、工具参数或正文。

Serve 必须提供 UAPI revision 7、所选 family 和实际启用的操作。能力关闭、当前授权不足或合同指纹不符时，应处理拒绝，不能切换 family 或重建操作规避。工具输出、offload 与档案材料须按对应能力协商；本指南不以某个 Serve 版本号替代这些检查。

Demo 正常成功退出为 `0`，由 Demo 报告的失败为 `1`；stderr 的 `code` 是本地 `ErrorCode` 数值，`status` 是 HTTP 状态（本地失败可能为 `0`），服务端错误还可能带 `wire` 和 `retry`。这些字段用于定位，不是通用重试许可。首次接入可按以下顺序排查：

| 现象 | 检查与处理 |
|---|---|
| CMake 找不到包，或程序无法加载/链接 | SDK 前缀指向保留完整目录结构的解压根；核架构、编译器、Release/CRT 和上表系统基线。变更工具链或前缀后用新 build 目录配置；直接运行 Demo 不需要 CMake |
| 凭据、journal 或档案路径被拒绝 | 核绝对路径、当前用户所有权、私有权限和全部祖先是否有链接/reparse。macOS 的 `/tmp`、`/var` 常是系统路径别名；对自己可信创建的目录确认物理路径后再传入，不为未知输入自动跟随链接 |
| 网络/TLS 错误，尚无有效 HTTP 状态 | 核 origin、DNS/网络、Serve 监听地址及证书链/主机名；Demo 不跟随重定向，应填写最终 Serve origin。企业 CA 处理见第 2 节 |
| 认证、能力或合同拒绝 | 核 token 与三个 scope 字段、原 family、Serve 装配和应用策略；`--require-output` 还要求输出能力。不要通过换身份、换 family 或自动去掉要求来掩盖拒绝 |
| 超时、非零退出或结果未确认 | 保留输出的 session ID、原意图、journal、档案和密钥；按第 4—6 节分别 attach/原意图对账/recover。不要把退出码当成业务从未执行的证明 |

公开开发使用 `python tools/contract_check.py --mode public`，核对分发声明中的 20 份原字节资产；内部 39 项参考与私有历史不随公开源码分发。[主线 CI](https://github.com/tansrai/tansr-cpp/actions) 和 [v0.1.0 发行记录](https://github.com/tansrai/tansr-cpp/releases/tag/v0.1.0)分别提供验证与制品入口。按发行记录核对三 OS 原生、真实 Serve、安装消费的证据及限制；本指南或 `--help` 成功不替代这些证据。第三方依赖许可见 [NOTICE](../packaging/NOTICE.md)。

## 专用 MemoryPublication 本地宿主（PST-05）

`<tansr/memory_publication.hpp>` 提供 `Store::execute(request, owner)` 纯存储端口，沿冻结 terminal-services-v1 的 head/read/begin/chunk/commit/query 六动作。owner 是原执行操作的 scope/sessionId/binding；权限由当前 Serve 和受信宿主决定。存储不提取记忆、不排序召回、不运行模型，也不改变 Archive、canonical、digest 或 ACK。4 MiB 正文、12 KiB 块按原协议核摘要、连续偏移和 UTF-8；同 transferId 同 begin 幂等，异体冲突，CAS 失败保留 conflict 终态。

`FileStore::open(Options)` 必须明确 create 或 reopen，传入绝对私有文件路径、身份、key_id、每次重读的 32 字节密钥 provider 和当前 scope provider。父目录由宿主使用 `storage::create_private_directory` 建立。新建不覆盖，重开缺文件不建空域；同目录独占锁沿原 PrivateDirectory。所有 publication 正文、暂存块、owner、transfer 回执以及 execution journal 的请求/结果一起 AES-256-GCM 加密后原子替换；AAD 绑定格式、身份与 key_id。错误密钥、缺钥、篡改、授权变化不交付明文，原件保留。密钥不得与 Archive 或另一 publication 介质共用；一把密钥最多 2^20 次加密，达到上限明确拒绝。显式新路径迁移及轮钥使用下述 `FileStore::migrate`；不能删除旧库/终态、换路径建空库或回滚旧备份绕过容量和计数。

`create_host({store, journal, authorize, true})` 既检查 store 的耐久/加密声明，也检查 journal 加密声明。FileStore 同时实现两者，返回的 tools 和 journal 必须一起交给原 ExecutorRunner。自定义 Store/Journal 可以分别注入，但不能把普通明文 FileJournal 配给要求加密的 publication host。`ToolContext.operation` 是原 Runner 给的操作副本，缺失不授权；宿主 authorizer 在执行前后复核当前操作身份与绑定。仅冻结 `MemoryPublication` 权限、`TansrTerminalMemoryPublication` 工具和原定义摘要可进入该 profile；不注册为模型工具或 Shell。

编译后的 `tansr-memory` 使用现有 Demo 的私有凭据/key 文件设施；`TANSR_ARCHIVE_KEY_FILE` 在这个进程中指向**专供 publication 的密钥文件**，不要指向已有 Archive 密钥。先由 Serve 管理员配置合法 Source/domain 和 MemoryPublication 权限，再挂接已有 session：

```sh
tansr-memory --session EXISTING_SESSION --binding-request ORIGINAL_BINDING_REQUEST_ID --file /absolute/private-memory/publication.bin --key-id memory-key-1 --source SOURCE_ID --generation 1 --domain DOMAIN_ID --create
# 重开原介质：使用同命令但去掉 --create，保留原 session/source/generation/domain/file/key。
```

Demo 注册专用 host，以空 tools 初始化并绑定，再通过原 `terminal.binding.create` 协商必需的 `memory-lifecycle-v1`，逐项核验返回 requestId、session、完整 binding（含 interpreter）、scope 和 accepted 后才显示 ready。通用 execution effectiveTools 名单不声明该辅助能力。原 Runner 每次检查 Serve execution status；受信宿主另行复核当前 scope/session/binding。先排空 Runner，再关闭介质与 Runtime。它不创建替代会话、不上传整包到另一个云索引，也不宣称设备离线时 Serve 可读取设备独有数据。新连接的旧 transfer query 默认拒绝；产品宿主可注入 authorize_recovery，并须核实原 Serve 恢复证明、旧授权撤销与当前连接许可；内建适配器同时限制相同 app/user/session/executor/workspace，仅放行只读 query，不转移旧写 owner。示例未配置跨连接恢复证明，不能把失败改成无条件 true。

绑定结果不确定时须保留原 binding requestId **与完整原请求体**。进程重启后重新注册 connection 会产生不同绑定；不得把新请求体放到旧 requestId 下，也不得用新键绕过未知结果。这个小型 Demo 不持久化 connection/binding 恢复意图，生产控制器须先对账原绑定；既有加密 operation/transfer 记录继续有效。单纯重开文件不授予新 owner 接续原 transfer 的权限。

`capacity()` 返回终态条数、暂存字节、journal 条数及剩余额度；配置在原文件内绑定，不静默更改。终态与原键不做 TTL 清除。原子替换后失败或提交后撤权返回 unknown，当前实例停止服务；关闭并按原身份/密钥重开，用原 transferId query 或原 operation journal 对账，不重做模型/工具。only-claim 在原 Runner 中保持 unknown。备份应在关闭后保存完整密文和外置密钥恢复策略；旧快照可能缺防重见证，不能直接回滚为当前权威库。应用日志、内存和系统 swap 不在本适配器加密声明内。

Windows 实证见开发台账。`integration/publication.py` 消费 SHA256 锁定的公开安装包 Serve Host，运行原生 C++ 进程与实际 Demo，失败时保留原临时目录。普通 Archive 验证不计为 publication 实证；Linux/macOS 与平台安装包仍需各自证据。
专用真实 Serve 工装需受信 Host 清单与精确公开包哈希，Host 本身不随 SDK 分发：

```sh
python integration/publication.py --manifest /absolute/shared-host.json --node /absolute/node --build /absolute/out/release --logs /absolute/new-evidence/native --suite native
python integration/publication.py --manifest /absolute/shared-host.json --node /absolute/node --build /absolute/out/release --logs /absolute/new-evidence/demo --suite demo
```

场景默认使用 `sdk1`。`--family sdk2-offload-v1` 需要 Host 已通过原公开 offload 宿主安装该族及 publication 配置；使用 SDK2 客户端本身不代表已安装该会话族。`capability_unavailable` / `not_installed` 不能通过改 header、回落旧族或另造 Source 绕过。新族创建在请求前保留原 requestId、完整 body 与绝对期限；不覆盖失回意图。

原生场景最多发送12条合成中文 pin，按实际提交的 publication 字节数达到12 KiB以上即停；未达到直接失败。每完成3条原交易后优雅关闭并重开 worker，保留原介质及 connection，每个进程仍有360秒总预算。原 pin 实现把锚点截为240字符，wire允许4096字符不代表会存储4096字符锚点。busy 仅在原回执查询确认未受理后同键同体有界重试。比较器以同一 transferId 核对 begin 总长/SHA、连续 chunk 偏移/摘要和 commit 长度/etag，不能用两次不同 transfer 的块凑多块通过。

工装在真实首块回执耐久后退出进程，重开原加密介质，以原 connection、operationId、digest、transfer 和 receipt 续提交；还在 Serve 实际受理后丢 HTTP 响应，按原状态对账，恢复不再进入存储 handler。原会话正常关闭并由受信 Host 核验公开 handle 的资源结算后，显式配置下一次源装配为 reopen，resume 原 session，在同 connection 上显式创建新 binding，再通过真实 read 核验全部块及完整 SHA。新 binding 只用于本次冷读，不能替换先前操作的身份。Host 对残存 lease 拒绝；未决命令不能被重开清除。only-claim→永久 unknown 在冷读之后独立验证。实际平台与候选通过情况见开发进度；整台 Serve 进程冷重启、跨主体接管与 Linux/macOS 不由此场景代签。

直接调用 `Runner::execute` 的宿主自行管理 heartbeat。外部 `Client::heartbeat` 返回的新期限不会修改已创建的 Runner；原期限到达后，已经写入但不能交付结果的操作仍须保留 unknown。串行静止点可以保存同 connection 的新期限并重建 Runner；`Runner::run` 则拥有内置心跳。不得因租约过期而重置 journal 或用新 operationId 重做。

### 显式迁移与轮钥

`FileStore::migrate(source, destination)` 只接受本 SDK 已支持的 `Tansr-Cpp-MemoryPublication/1` 加密格式。先停止原 Runner 并关闭原 Store；source 必须 `create=false`，destination 必须 `create=true`、位于**另一私有目录**且目标文件不存在。调用过程中同时持有两端排他锁，不接受运行中的源，也不自动创建父目录。原 app/user/sourceId/sourceGeneration/domainKey 必须完全相同，目标仍重核当前 scope/密钥。允许明确设置新的容量；原事实不能容纳时在目标发布前拒绝。

目标必须使用**从未供其他介质使用的新 key_id 和独占密钥**，实际 32 字节密钥也必须不同于源。仅改名称不会通过；迁移不开放同钥复制，因为分叉的快照计数不能证明同钥总用量。新钥计数从第一次完整快照加密开始。密钥 provider 由宿主管理，不能在迁移失败时自动生成另一把钥再试。

```cpp
// 两份 Options 都具有真实当前 scope/密钥回调；不得伪造身份。
auto source = current_options;
source.create = false;
auto destination = source;
destination.path = new_private_directory / "publication.bin";
destination.create = true;
destination.key_id = fresh_key_id;
destination.read_key = read_fresh_exclusive_key;
auto made = tansr::storage::create_private_directory(new_private_directory);
if (!made) return made.error();
auto migrated = tansr::memory_publication::FileStore::migrate(source, destination);
if (!migrated) return migrated.error();
// 保存 migrated.value() 的版本、身份、两端密文 SHA256/字节数和事实计数。
// 由宿主明确选择唯一活动路径后，以 destination.create=false 重开。
```

首次原子发布即为完整导入快照，没有先创建空库的中间态。正文、所有 committed/conflict/staging transfer、原 owner、部分块、operationId/原摘要/截止、已知 receipt、unknown receipt 和 only-claim 全部原样保留；共存的加密 execution journal 一起迁移，不能只复制正文。函数不执行工具、不改变 Serve 绑定或恢复许可，也不把旧 pending 标为已完成。结果 `MigrationReceipt` 仅包含本介质版本、范围、两端密文 SHA256/字节数及 transfer/journal 条数；它不覆盖外部会话、预算、其他快照或密钥。结果只在完整提交并复验两端后返回，两端锁随后释放。

故障时保留原件；目标可能不存在或已经是完整新快照，提交后的失证报 `unknown`，不声称迁移未发生。不要删除目标或覆盖原件自动重做；保留两端和两把密钥，以原配置显式重开、核验完整快照和原操作后再选择活动路径。错误钥、未知格式、篡改、缺原件、错主体均拒绝，不创建空库遮掩。源内容始终不因迁移改变，但旧副本不是当前权威库：迁移后禁止两份同时接入 Runner；目标接收新事实后，不得切回旧快照绕过防重。离线旧件供核验与在**尚未产生新事实**时显式回退；迁移工具不提供跨副本双写或自动接管。

Demo 提供无网络的显式迁移模式，沿原私有 scope/token 文件读取当前身份；该模式不需要 `--session`，也不注册/绑定会话：

```sh
# TANSR_ARCHIVE_KEY_FILE 仍指向原 publication 专用钥。
export TANSR_MEMORY_NEXT_KEY_FILE=/absolute/private-keys/fresh-memory-key.hex
tansr-memory --file /absolute/private-memory/publication.bin --key-id memory-key-1 --source SOURCE_ID --generation 1 --domain DOMAIN_ID --migrate-to /absolute/private-memory-next/publication.bin --new-key-id memory-key-2
# 校验回执后，将 TANSR_ARCHIVE_KEY_FILE 明确改为新钥，host 的 --file/--key-id 改为目标；不加 --create。
```

`--migrate-to` 不能与 `--create` 合用。先保留原件与原钥，再按宿主许可完成单路径切换；成功打印只代表本地快照迁移完成，不代表 Serve 已绑定新路径或业务恢复完成。

## 显式 TerminalPersistence v1 profile（PST-05）

`<tansr/terminal_persistence.hpp>` 提供 `terminal_persistence::FileStore` 和 `create_host`。这是用户批准 RFC-PST-1 后新增的独立 `TansrTerminalPersistenceV1` 工具；旧六动作、旧默认工厂、旧合同资产及旧 `Tansr-Cpp-MemoryPublication/1` 文件仍按原义读取。新 `Tansr-Cpp-TerminalPersistence/1` 文件不会被旧工厂接收；显式 v1 不支持时拒绝，不自动降级。

新 Store 只存不透明正文块/描述页、双键 Entry/value、Root 和永久 transfer。正文按 12,288 字节固定边界，最多 4 MiB；每次最多 256 个索引 entry。body 摘要与整体 commitRoot 分离；read/lookup 必须携带当前 commitRoot。head 的 count/root 来自同一快照。新增永久 ordinal、双键索引、正文根、transfer committed/result 和容量引用保护在一次 AEAD 快照原子替换中生效；query 永久返回该 transfer 的历史完整 Root，不把当前根冒充旧结果。未接收的对象只可由已验描述页授权，复用只来自受保护的 base 或完全相同的既有永久 entry。索引不判断回执业务终态。

```cpp
namespace tp = tansr::terminal_persistence;
tp::Options options;
options.path = private_directory / "persistence-v1.bin";
options.create = true; // 后续明确 false；原件丢失必须报错
options.identity = trusted_source_identity; // scope app/user + sourceId/generation/domainKey
options.key_id = dedicated_fresh_key_id;
options.read_key = current_key_provider;
options.read_context = current_scope_provider;
auto store = tp::FileStore::open(options);
// 处理 Result 后，将 tools 与 journal 一起交原 Runner；authorize 核原操作/当前绑定。
auto host = tp::create_host({store.value(), store.value(), current_authorizer, true});
```

`Store::execute(request, owner, guard)` 的 owner 来自已验原 Operation，guard 是原操作当前授权/取消检查。主机适配器自动提供 guard，贯穿私有目录和原子写 IO 边界；变更发生于提交后仍可能已写，结果保 unknown 并按原 operation/transfer 查询。直接纯存储调用者承担同样的可信配置责任。`authorize_recovery` 仍只允许原同域/session/executor/workspace 的 query；它不能给新连接接续 put/commit。永久 execution claim/完整 receipt 也在同一加密介质，pending/unknown 不重新授执行。

实际默认容量：active transfer 32、staging raw 8 MiB、永久 entry/transfer/object 各 4,096、逻辑 retained+reserved 32 MiB、journal entry 8,192、单密文文件 64 MiB。可显式降低，head 回报实际逻辑 limits/used。对象 raw 和 canonical 描述、ordinal/entry、原 begin/owner/base/result、当前 Root 按统一规则计量，begin 预留 declared 与 262,144 字节元数据；文件、未来执行日志和每钥小于 2^20 次写入另有保守余量。无关查询或新操作不能吃掉已受理计划的必要结算余量；介质/钥余量不足明确拒绝，既有事实保留。已打开目录持有跨进程独占锁。

此版本每次写入和冷开审核整个加密快照，查询为内存扫描；不宣称 O(1)、百万条索引或 1 GiB 实际能力。原子替换时旧文件和新临时密文可能同时存在，宿主至少按两倍实际 max_file_bytes 规划空间；这不是 OS 磁盘预分配或断电 SLA。磁盘满/同步失败可回 unknown。文件及临时文件全部加密，永久 receipt/transfer 不按 TTL 逐出；当前版本没有物理 GC，满额拒绝而不删旧见证。

原 Demo 显式 opt-in：

```sh
tansr-memory --profile persistence-v1 --session EXISTING_SESSION --binding-request ORIGINAL_BINDING_REQUEST_ID --file /absolute/private-v1/persistence.bin --key-id dedicated-v1-key --source SOURCE_ID --generation 1 --domain DOMAIN_ID --create
```

Serve 必须显式安装/选择同一 v1 profile；不改旧四项 capability 数组或路由。省略 `--profile` 继续原 publication。不得在同一域同时运行两个可写 profile。Demo 没有跨 owner 的自动接管或绑定未知恢复功能；保留原绑定请求和完整 body，原结果未结算前不重发异体。

同格式 v1 的 `FileStore::migrate(source,destination)` 与 Demo `--profile persistence-v1 --migrate-to NEW_PATH --new-key-id NEW_ID` 复用既有保源新路径维护：先停 Runner，源 reopen，目标 create+另一私有目录+从未用于其他介质的新 key_id/实际新钥；完整快照第一次发布就包含所有对象、索引、Root、pending/unknown/终态和 journal。目标已存在拒绝，容量不够不删源。发布后失回保两端并原配置重开对账。目标的认证快照持久记录只读状态：普通冷开仍允许 head/read/lookup/query，拒绝 begin/put/commit。C++ journal 与正文同文件，因此也拒绝新增 execution claim（包括读取动作）和完成既有 pending；原 pending/receipt 仍可按原键查询，重复相同已存 receipt 是无写幂等。没有激活开关。此复制仅供核验/取证，不承诺从复制件接管执行或切为可写。源与原写预算计数不变；没有共同源围栏时维护工具不能授权第二个 writer。

旧六动作库向新 profile 的业务格式转换不由这个纯存储工具猜测。可信上层须保留旧文件/钥/历史 query 路径，先证明旧 writer 停止和 unknown 已结算，再明确建立新 v1；没有共同切换证明就保持待切换，不靠文件存在自动选择。

每次 AES-GCM 加密尝试先耐久扣减相邻 `<file>.writes` 侧文件计数，包括随后快照替换失败的尝试。侧文件仅含随机 store ID、身份摘要、key ID 和经 HMAC-SHA256 认证的计数，不含明文正文、索引、owner 或回执，也不再使用 GCM。缺失、认证失败或低于快照的计数拒绝重开。关闭后备份须成对保留；首次根发布失败留下的孤立计数保留原状并阻止 `create`。同格式迁移校验原文件对，仅在显式新独占密钥下建立新 store ID/计数。迁移回执中的 SHA 指主密文快照，仍须保留对应计数。打开的实例可检测计数被替换，但完整旧快照/计数对重放，或失败尝试未形成新快照时回放旧计数，缺少外部单调见证便无法识别；不能恢复旧副本或重置计数来腾容量，也不声称全目录防回滚。
